# Windows smart-card signing acceptance

Automated tests use synthetic certificates and injected Win32/cryptographic seams. They verify RSA, P-256 and P-384 embedded PDF signatures, one actual signature callback per operation, provider routing, cancellation/resource lifetime, native ABI arguments, CSP RSA byte reversal, and failure classification. They do not prove ActivClient/OpenSC, a real smart card, or native PIN UI behavior. The following manual acceptance checks remain unrun.

1. Install the reader driver and ActivClient or OpenSC matching the process architecture. Use a dedicated test card whose captured PIV 9C certificate appears exactly once in the current user's Personal store. Retain unrelated certificates to confirm selection does not prompt for another card. Do not record card identifiers or PINs in diagnostics.
2. Select the Windows physical signing backend and certify a synthetic report. Confirm the middleware PIN dialog belongs to the application window, the application PIN overlay is absent, the private key remains on the card, and only one signature is requested. Independently verify the embedded PDF signature and certificate binding in a PDF verifier.
3. Repeat for supported RSA CSP `AT_SIGNATURE`/`AT_KEYEXCHANGE`, RSA KSP, ECDSA P-256 KSP, and ECDSA P-384 KSP cards. Windows RSA key technology follows the returned key specification, not the certificate's RSA algorithm. Unsupported provider/curve cases must fail safely.
4. With administrator-approved test cards, exercise wrong PIN, locked PIN, native Cancel, removal during signing, and mismatched reader/certificate. Confirm no automatic retry, PKCS#11 fallback, issuance commit, or replacement of an existing issued report. Do not intentionally lock a production credential.
5. Cancel the application flow while a native PIN dialog is open. Confirm new presence/signing requests remain gated until the native operation returns, and cancellation leaves working/issued reports unchanged. After dismissal, verify the next card operation succeeds without retained handles.
6. Select the Pkcs11 physical signing backend and configure a valid explicit module path. Confirm PKCS#11 is authoritative. Configure an invalid path and confirm the configuration failure does not open Windows PIN UI. Exercise the Windows and Pkcs11 backends separately. Change settings while a prepared session is open and confirm it stays on the selected provider.
7. Run the setup diagnostic with and without middleware/store access. Confirm it shows only configuration/store availability and never opens a PIN dialog or requests a private key. Check headless composition rejects Windows interactive signing before acquisition.

Native contracts follow Microsoft documentation: [CryptAcquireCertificatePrivateKey](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptacquirecertificateprivatekey), [key storage properties](https://learn.microsoft.com/en-us/windows/win32/seccng/key-storage-property-identifiers), [CryptGetProvParam](https://learn.microsoft.com/en-us/windows/win32/api/wincrypt/nf-wincrypt-cryptgetprovparam), and [NCryptSignHash](https://learn.microsoft.com/en-us/windows/win32/api/ncrypt/nf-ncrypt-ncryptsignhash). Acquisition uses `PREFER_NCRYPT | COMPARE_KEY | WINDOW_HANDLE`, with the address of the HWND, without SILENT/CACHE. Returned key ownership follows `callerFree`; a borrowed key keeps its original certificate context alive. The provider reference returned by `NCRYPT_PROVIDER_HANDLE_PROPERTY` is separately released per the documented property contract. CNG uses one known-size signature buffer, SHA256 PKCS#1 padding for RSA and no padding for ECC; CSP uses SHA256/HP_HASHVAL and reverses its little-endian RSA signature. ECDSA native fixed-width P1363 values are converted to DER for PDF signatures.
