# Phase 4 — Build & system info surface

**Parent:** [platform-roadmap.md](../platform-roadmap.md)
**Depends on:** [Phase 3](phase-3-configuration-model.md) (shares the Diagnostics panel)
**Unblocks:** [Phase 5](phase-5-schema-versioning.md) (needs a version constant), [Phase 6](phase-6-crash-reporting.md) (a crash report without a version is nearly useless)
**Status:** Done

## Goal

Make it possible to answer "what exactly is running on this bench?" from inside the application, from a log file, and from a test record — without asking anyone to check a file date.

## Why

There is no version anywhere. `src/HardwareTest/app.manifest` hardcodes `1.0.0.0`, no `.csproj` sets `VersionPrefix`, and nothing reads an assembly version at runtime.

The sharpest consequence is a traceability gap: `TestRunRecord` records the DUT, the operator, the plan, and the verdict, but **not the software that produced the verdict**. For a hardware test record that is an audit hole — a re-run that disagrees with a stored result cannot be attributed to a software change.

## Locked rules

- Version metadata is **generated at build**, never hand-maintained in a file someone must remember to bump.
- The build must work in a plain `dotnet build` with no git and no CI — degrade to a `local` marker rather than failing.
- Reading your own assembly's attributes is AoT-safe; do not introduce a reflection-heavy version library.

## Work items

1. **MSBuild version stamping** in [`Directory.Build.props`](../../Directory.Build.props):
   - `VersionPrefix` as the single source of truth (start `0.1.0`).
   - `SourceRevisionId` from `GITHUB_SHA`, falling back to `git rev-parse --short HEAD`, falling back to `local`.
   - `InformationalVersion` = `{VersionPrefix}+{sha}` (deterministic for a given commit). Build time is **not** part of the version string — [Phase 20](phase-20-ci-honesty.md) stores git committer date as `AssemblyMetadata` `CommitDate` instead of embedding `DateTime.UtcNow`.
   - `ContinuousIntegrationBuild=true` when `CI` is set, which pairs with the `Deterministic` flag already enabled.

2. **`BuildInfo` in Core** — an immutable record read once at startup:

   | Field | Source |
   | --- | --- |
   | `Version`, `InformationalVersion`, `CommitSha`, `BuildTimestampUtc` | assembly attributes |
   | `RuntimeVersion`, `RuntimeIdentifier`, `OsDescription`, `ProcessArchitecture` | `RuntimeInformation` |
   | `IsSelfContained`, `ProcessStartUtc` | host environment |
   | `OpenTapEngineVersion` | OpenTAP assembly — resolved in Host, not Core, to keep Core OpenTAP-free ([Phase 2](phase-2-architecture-tests.md) rule 2) |

3. **Surfaces:**
   - **Settings → About/Diagnostics** card above the Phase 3 provenance table: version, commit, build date, runtime, RID, OpenTAP engine, data directory. One **Copy diagnostics** button producing a paste-ready support block.
   - **Startup log**, one Information line, first thing after logging initializes.
   - **Window title** carries the version suffix in Debug and Engineer mode only — not in front of operators.
   - **`--version`** prints the informational version and exits.

4. **Traceability stamping** — add `AppVersion` and `AppCommitSha` to `TestRunRecord`, written at run start (not at report time, so an aborted run still carries them). Register the new fields in [`AppJsonContext`](../../src/HardwareTest.Core/Serialization/AppJsonContext.cs) — with reflection-based JSON disabled, an unregistered field is a runtime failure on a bench.

5. **Report footer** — thread the version through the Typst inputs already assembled in [`TypstReportService`](../../src/HardwareTest.Core/Reporting/TypstReportService.cs), which currently hardcodes `"Generated by HardwareTest."`. Update `status-report.typ` and `certification-report.typ`. A certification PDF in particular should name the software that produced it.

6. **Log correlation fix (adjacent, cheap)** — the console output template references `{TestRunId}` but nothing ever pushes that property, so it is always blank. Push it via `LogContext` for the duration of a run while you are in this code.

## Tests

- `BuildInfo` populates non-empty `Version` and `InformationalVersion` in a normal test run.
- A run record round-trips `AppVersion` through `FileRunStore`.
- `AppJsonContext` covers the new fields (asserted by the [Phase 2](phase-2-architecture-tests.md) registration test).
- `--version` exits `0` and prints a parseable version.

## Exit criteria

- [x] Settings shows version, commit, runtime, and OpenTAP engine version.
- [x] **Copy diagnostics** yields a support block that identifies the build unambiguously.
- [x] Every new `run.json` names the software version that produced it.
- [x] A local `dotnet build` with no git present still produces a usable `InformationalVersion`.

## Out of scope

- Auto-update and release channels.
- Backfilling `AppVersion` into historical run records — legacy records report "unknown" ([Phase 5](phase-5-schema-versioning.md) defines how).
- A public release/tagging workflow.
