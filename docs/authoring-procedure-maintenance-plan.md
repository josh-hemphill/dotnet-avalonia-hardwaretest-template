# Advanced procedure editing and maintenance in Authoring

An engineer should be able to open the Advanced Fixture Procedure in HardwareTest Authoring, find a test and the data it uses, change both, preview the effect, and ship a package that runs from a clean installation. Use that procedure as the acceptance fixture. The first release should cover a useful maintenance task end to end: change a switch route or pass band, verify the affected cases in simulation, and package the revision. The full plan extends that workflow to procedure structure and plugin-backed analysis. [Advanced Fixture Procedure](../examples/AdvancedProcedure/README.md)

The current import shows the fixture as one read-only raw node with 42 nested steps. Saving an inspection copy inserts a group above the fixture root, which causes fixture preflight to fail. General workspace packaging currently enumerates plans and their sidecars. The example’s tables travel through its separate staging command. Both paths need to work before engineers can rely on edits made in Authoring. [Authoring workflow evidence](../examples/AdvancedProcedure/council-ux-review.md#authoring-boundary) · [Package file enumeration](../src/HardwareTest.Authoring.Core/PackageXmlRenderer.cs)

## 1. Preserve imported procedures and package their inputs

- Extend the import and export contract to preserve step IDs, order, parentage, plugin settings, links, sidecars, and references to external files. Show raw subtrees as navigable, read-only content with their plugin requirements. If a plugin is missing or an export cannot preserve a subtree, keep the source available for inspection and block the affected export with a diagnostic that identifies the step and recovery action. [Compiler import](../src/HardwareTest.Authoring.Core/PlanCompiler.Load.cs) · [Compiler export](../src/HardwareTest.Authoring.Core/PlanCompiler.Save.cs)
- Declare portable program assets and plugin dependencies in the workspace. Capture the exact plan, sidecar, data files, and dependency versions for a build. Resolve data paths consistently when opening, validating, and running an installed package. Extend the existing document sessions and build pipeline for compatibility, conflict handling, and recovery. [Authoring architecture](authoring-app.md#document-sessions-and-editing) · [Build service](../src/HardwareTest.Authoring.Core/AuthoringBuildService.cs)
- **Release gate.** Import the example, save and reopen a copy, package it using Authoring, and run the complete simulation in a clean Operator and Worker install. Compare normalized plan structure, required files, and expected verdicts against the existing example. Verify that existing version 2 workspaces still open and build, and exercise an unresolved plugin, an opaque subtree, and an interrupted save.

## 2. Edit routes, limits, and reference data in context

- Add structured data to workspace definitions, with links in both directions between a test and its referenced rows. Support search, filtering, and editing of switch maps, case tables, stimuli, limits, and reference traces. Use stable row IDs and shared validation across the editor and CLI. Surface invalid units, duplicate IDs, broken joins, and inverted limits at the affected cell and test. Show affected tests before a shared edit or deletion.
- Give program and station values explicit ownership. Keep procedure inputs and thresholds with the procedure. Let station maintainers manage station profiles and calibration as versioned records. Show the route, impedance, approved calibration revision, and effective correction used by a test. If a required station value is missing or incompatible, point to the exact lookup and block the affected run during preflight.
- Include structured edits in Undo, Save All, and external-change handling. Provide a row-level comparison that identifies changes to effective values. Offer a recorded-data preview for criteria where replay is supported and a simulation path for changes that affect acquisition, including switch routing. [Existing session and edit contracts](authoring-document-session-spec.md) · [Example table layout](../examples/AdvancedProcedure/README.md#change-a-route-criterion-or-measurement)
- **Release gate.** An engineer can open a failing rail or attenuation case, follow it to the route and test values, change a route and a pass band, review the affected cases, save and reopen, and ship the simulated revision. Reverting the edit restores the previous values and behavior.

## 3. Edit suites, prerequisites, and operator choices

- Extend the sequence editor to show sections, suites, and tests with stable identities. Support search, collapse, keyboard navigation, and safe moves in a long procedure. Keep test purpose and setup notes with the items they describe. Put prerequisites and their dependents in the selected item’s inspector. Flag cycles, missing references, and moves that would invalidate required execution order. [Sequence model](../src/HardwareTest.Authoring.Core/AuthoringSequence.cs) · [Dependency index](../src/HardwareTest.Authoring.Core/AuthoringDependencyIndex.cs)
- Represent station bring-up and calibration checks, connector self-test, and DUT bring-up as reusable prerequisites within a run. A successful prerequisite can satisfy several suites once per run. Show which failed prerequisite blocked each dependent suite, and allow eligible independent measurements to continue. Keep selection, retries, and resume subject to prerequisite validity and the active fixture state.
- Add an editor for operator handoffs and required physical configurations. Each choice names the physical setup and links to its suite. Reuse the Operator interaction in preview so the author can confirm the handoff wording, choose configurations in any order, and see progress and the remaining choices. Keep failed-attempt history visible when a choice is retried.
- **Release gate.** An engineer can add a suite, connect it to shared prerequisites, and edit a fixture choice in Authoring. Simulation covers successful bring-up, a failed prerequisite, an independent suite failure, a guarded selected run, and completion in different orders. Save and reopen preserves the same dependencies and choices.

## 4. Maintain plugin-backed tests and verify the evidence

- Add a versioned editor contract for registered measurement and instrument plugins. Start with the example serial DUT instrument and a shared-capture analysis. Let authors edit typed settings, bind instrument slots and data inputs, select reference data, and set named outputs with units and lower and upper score thresholds. Plugin maintainers own serial transport, decoder logic, and other custom analysis in their plugin projects. [Serial DUT starter](../examples/AdvancedProcedure/README.md#serial-dut-starter)
- Use the selected recording or simulation to show how one acquisition produces several evaluated rows. Surface the final value, limits, score or verdict, and row identity alongside the source capture. Cover residual and curve deviation, delta to the previous step and to reference, full-span comparison, reciprocal paths at multiple impedances, and waveform compliance alongside decoded values.
- Extend run evidence so a reviewer can trace each row to its exact UTC timestamp, attempt, configuration, and applicable limits, then to the procedure revision, data and calibration revisions, and input file digests. Keep stable row identities across display name changes. Verify the same row in Operator Results, the persisted run, and report output. [Example evidence and reports](../examples/AdvancedProcedure/README.md#evidence-and-reports)
- **Release gate.** A maintainer changes a plugin setting or profile in Authoring, reopens it, and runs a packaged simulation. A reviewer can trace a failing row from the report to the specific edited input and shared capture. A missing plugin or incompatible input or output definition produces a targeted diagnostic before execution.

## Council workflow and interface reviews

Review a working prototype after the route and limit milestone and the staged desktop build before release. Give reviewers realistic tasks and the Advanced Fixture Procedure with enough cases to exercise navigation. Ask them to record completion, wrong turns, recovery, and any action that could silently change execution or evidence. Use keyboard and pointer walkthroughs in compact and wide layouts. File blockers against their release gates and rerun the affected variants after fixes. [Previous Council workflow variants](../examples/AdvancedProcedure/council-ux-review.md#workflow-variants)

| Role | Workflow variants | What the review should verify |
| --- | --- | --- |
| Procedure engineer | Maintain a single test, change a shared row, reorder a nested suite, recover an edit after an external change | Find the owning data from the test, identify every affected suite, and recover without losing work. |
| Station maintainer | Inspect a route at either impedance, load a new calibration revision, encounter a missing lookup | See which values are effective for the station and resolve the specific routing or calibration issue. |
| Operator | Complete configurations in different orders, retry a failed choice, encounter failed bring-up or an interrupted run | Understand what is being requested, what remains, and why a suite is blocked. |
| Plugin maintainer and release reviewer | Inspect an unsupported step, restore a missing dependency, ship from a clean workspace, audit a failed row from an earlier attempt | Preserve custom content through maintenance and reproduce the package and the row’s inputs from recorded evidence. |

Start with the round-trip and package gate, then release the table-editing workflow as the first end-to-end slice. Use simulation and recorded captures for repeatable acceptance. Add a physical bench check when qualifying a product’s serial adapter, switch map, and station calibration for deployment.
