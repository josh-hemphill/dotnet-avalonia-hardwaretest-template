# Saved shell-app build inputs

The authoring build snapshot supports the repository's real `HardwareTest.ShellApps.Notes` SDK project, including its `HardwareTest.Shell.Abstractions` reference, Avalonia resources, centrally managed PackageReferences, repository build configuration, and package locks. A manifest may refer to a project outside the authoring workspace.

Capture evaluates project references and source items without running MSBuild targets or modifying original project `obj` directories. It freezes the bounded common source hierarchy, ancestor `Directory.Build.*`, `Directory.Packages.props`, NuGet configuration, `global.json`, editor configuration, existing resolved assets when present, and the full payload of every resolved NuGet package. Package folders in existing assets are honored. Restore always evaluates a disposable copy of the saved sources using the same Release configuration as publication, including SDK-inferred runtime and app-host download dependencies that package locks omit; offline requests use cache-only restore. SDK and host identities are also captured by the build service. The full declared SDK home remains an identity input, including installed SDK/runtime/pack membership; identity-only reads stream hashes through a pooled buffer without retaining payload bytes or trusting timestamps. Ordinary files reuse their already resolved directory target, while file links still receive full physical target resolution.

Preparation publishes from copied source and package payload bytes. Its NuGet configuration clears remote sources, uses the staged package folder, disables audit, and supplies fixed revision metadata so repository version targets do not consult live git state. Original resolved assets remain identity inputs; staged restore regenerates assets for staged paths. Publication rechecks all input hashes and link targets, including source tree membership, package payloads, resolved assets, and SDK identity.

Each SDK write operation consumes a shared immutable global-property profile through explicit MSBuild `Restore` and `Publish` targets. The same profile is evaluated without targets on the actual disposable/staged project paths first, using the same frozen environment. Checks include the complete selected project-reference closure and standard reference-build projections of publishing globals; identity expressions conditioned on revision metadata, restore flags, publishing flags, destination or copied paths must resolve safely before any write target runs. Project-reference metadata that overrides the checked global profile is unsupported. The repository's accepted version targets may only set revision/informational metadata, not SDK output identities. Capturing and staging never rely solely on an original-path Release-only evaluation.

Inherited MSBuild output, intermediate, import, compiler-input/tool, workspace, restore and cache redirect properties are rejected before SDK evaluation or restore. This includes `OutputPath`, `BaseOutputPath`, `OutDir`, `MSBuildProjectExtensionsPath`, `DirectoryBuildPropsPath`, `RestorePackagesPath`, `RestoreConfigFile` and custom NuGet cache overrides, even when their values are relative. Clear these inherited overrides to use the owned staging profile. Standard SDK resolver/tool path bindings are allowed only as unambiguous absolute paths physically contained in the declared `DOTNET_ROOT`; ordinary custom flags such as `DefineConstants` remain frozen inputs. The declared `NUGET_PACKAGES` payload cache remains supported and is copied into staging.

The same profile rejects generated-source/editorconfig, reference-assembly, deps/runtimeconfig, compiler log/generated-file, package/nuspec, artifact-layout, cleanup and reference-cache path overrides. This includes the reference-copy folder alias `RefAssembliesFolderName`; copy-output metadata (`Link`, `LinkBase`, `TargetPath`, `RelativePath`, and `DestinationSubDirectory`) must stay within literal relative paths in both item attributes and child elements, matching MSBuild identifiers without case sensitivity. Item/reference discovery, override guards and SDK JSON metadata lookup use the same case-insensitive identifier rules; reserved XML structural tags retain SDK syntax requirements. Property, item and metadata expressions, MSBuild percent escapes, and traversal/rooted forms are rejected before SDK evaluation, rather than trusting a pre-target projection of copy destinations. Project references cannot supply `UndefineProperties` to remove checked globals. SDK filename aliases such as `TargetName` cannot redirect outputs; assembly/package/framework/runtime identities must not contain path components, and their evaluated values are checked before restore. Inherited private SDK properties (underscore-prefixed names, except platform bindings `__CF_USER_TEXT_ENCODING`, `__CFBundleIdentifier`, `__COMPAT_LAYER`, `_JAVA_OPTIONS` and the SDK launcher's `_MSBUILDTLENABLED` terminal-logger flag) are rejected rather than forwarded into future SDK cache/output targets. Source configuration cannot override private SDK properties; the repository's two private git-date helpers remain supported by its fixed version targets. This guard covers the documented standard SDK profile and named path properties; it does not claim safe execution of arbitrary SDK extensions or dynamic MSBuild graphs.

The common source root must be bounded below the filesystem root. Project references must be literal relative paths. Explicit absolute or dynamic source paths, external source globs, multi-targeted graphs, custom SDKs, custom tasks, arbitrary custom targets, externally redirected intermediate/package/output directories, and imports with dynamic or absolute paths are rejected with `BUILD_SHELL_INPUTS`. SDK-discovered absolute analyzer paths inside the captured SDK/package payloads and editor configurations on the project ancestor chain are supported through the captured hierarchy. Other evaluated absolute-input errors identify the item kind and path. The repository's two version-stamping targets are supported with fixed staged revision properties. This is a deliberately bounded graph capture, not a sandbox for arbitrary MSBuild code.

`AuthoringBuildShellGraphTests` exercises the real external Notes graph through publication, confirms that original project intermediates stay unchanged, and checks invalidation after project, referenced-project, central-configuration, lock, and copied NuGet payload changes. The package mutation fixture owns a separate temporary cache, including inferred NetCore, AspNetCore and WindowsDesktop runtime/reference families; a platform-independent cache-copy fixture verifies those payloads are retained. It never alters the user's shared package cache.
